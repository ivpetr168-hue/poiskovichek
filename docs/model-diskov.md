# Модель скорости дисков

Зачем: индексирование читает файлы с разных дисков. Если все потоки берут файлы из одной очереди,
медленный жёсткий диск задерживает их, а быстрые диски простаивают. Модель отвечает на вопросы:
сколько потоков чтения давать каждому диску, складываются ли диски при одновременной работе,
где предел — диск или процессор.

## Как измерено

Программа `zamer_diskov` (исходник `src/bin/zamer_diskov.rs`, чтение — `src/zamer.rs`):

```
podgotovka → наборы файлов на каждом диске (папка ПоисКовичеК-замер с файлом-меткой)
opyty      → опыты A–E, каждая ячейка ограничена временем, итог — CSV
model_diskov.py → подгонка модели по CSV, отчёт и JSON
ochistka   → удаляет только папки с файлом-меткой
```

- Чтение идёт мимо кэша Windows (`FILE_FLAG_NO_BUFFERING`), прав администратора не нужно.
- Наборы: `melkie` 10 000 × 4 КБ, `srednie` 2 000 × 200 КБ, `krupnye` 25 × 20 МБ.
- Каждая ячейка — 3 повтора на свежих файлах; свежие кончились — чтение по кругу (`povtor=da`).
- Модель: время на файл у одного читателя `t(s) = α + s/β`; масштабирование по числу читателей —
  USL `X(k) = λk / (1 + σ(k−1) + κk(k−1))`.

Опыты:

| Опыт | Что измеряет |
|---|---|
| A | каждый диск отдельно × k ∈ {1, 2, 4, 8} читателей × три набора |
| B | порядок чтения на HDD: по папкам, по номеру записи MFT, случайно |
| C | пары и тройка дисков одновременно, k = 1 и 4 на каждом |
| D | разбор текста без диска (`extract_bytes`), 1, 2, 4 потока, по форматам |
| E | чтение C: при одновременной записи на тот же и на другой диск |

## Замер 26.10.2026

Машина: ноутбук, AMD Ryzen 3 4300U (4 ядра). Диски: C: — NVMe SSD, D: — SATA HDD,
P: — SSD по USB. Подготовка наборов — 2,3 мин, опыты — 192 ячейки за 10 мин 10 с.

### Суммарная скорость чтения одного диска, МБ/с (опыт A)

| Диск | Набор | k=1 | k=2 | k=4 | k=8 |
|---|---|---|---|---|---|
| C: NVMe | 20 МБ | 1737 | 2017 | 2093 | 2217 |
| C: NVMe | 200 КБ | 375 | 803 | 1427 | 1830 |
| C: NVMe | 4 КБ | 12 | 26 | 46 | 62 |
| D: HDD | 20 МБ | 72 | 72 | 68 | 49 |
| D: HDD | 200 КБ | 82 | 86 | 89 | 97 |
| D: HDD | 4 КБ | < 1 | 1 | 1 | 1 |
| P: USB SSD | 20 МБ | 324 | 394 | 394 | 394 |
| P: USB SSD | 200 КБ | 179 | 336 | 381 | 390 |
| P: USB SSD | 4 КБ | 14 | 30 | 55 | 91 |

Что это значит:
- SSD выигрывают от нескольких читателей, особенно на мелких и средних файлах: время уходит на
  открытие файла и задержку, а не на передачу.
- HDD упирается в перемещение головки: мелкий файл стоит около 7–8 мс (~130 файлов/с). Больше
  двух читателей ему не помогают, а на крупных файлах восемь читателей снижают скорость на треть.
- USB SSD упирается в шину около 390 МБ/с уже при двух читателях.

Задержка α на файл у одного читателя: NVMe 0,3–0,4 мс, USB SSD 0,15–0,4 мс, HDD 3–15 мс.

| Формат | 1 поток | 2 потока | 4 потока |
|---|---|---|---|
| pdf | 2,5 | 4,7 | 8,7 |
| txt | 25,7 | 50,3 | 85,6 |
| docx | 35,4 | 68,4 | 115 |
| html | 61,2 | 123 | 220 |

Четыре потока ускоряют разбор в 3,3–3,6 раза. Разбор медленнее чтения с любого SSD, а PDF —
медленнее даже HDD: на типичной коллекции документов предел индексирования — процессор.

### Помехи записи (опыт E)

| Запись во время чтения C: | Чтение медленнее в |
|---|---|
| на тот же диск C: | 2,9 раза |
| на другой диск D: | 1,5 раза |

### Порядок чтения на HDD (опыт B)

D: HDD, один читатель, файлы по 4 КБ. Перед каждой ячейкой буфер диска вытесняется чтением
500 МБ; у каждой ячейки своя доля свежих файлов (~1 100), по кругу не читается.

| Порядок | Файлов/с | Относительно «по папкам» |
|---|---|---|
| по номеру записи MFT | 3362 | 1,39 |
| по папкам (порядок обхода) | 2424 | 1 |
| случайно | 1934 | 0,80 |

Вывод: порядок обхода папок близок к лучшему; сортировка по номеру MFT даёт ещё ~1,4 раза,
случайный порядок теряет 20 %. Абсолютные числа здесь в 15–30 раз выше, чем в опыте A
(74–159 файлов/с при одном читателе): к опыту B служебные записи файловой системы (MFT) уже
лежали в памяти Windows, и диск читал только данные. При первом индексировании они холодные —
верная оценка для него — опыт A. Там же видно: второй читатель на HDD ускоряет мелкие файлы
в 6–8 раз (770–955 файлов/с) — диск сам упорядочивает очередь запросов.

Первый вариант опыта B (тот же набор после опыта A, ячейка читала по кругу) недостоверен:
файлы отдавал буфер диска.

## Что из этого следует для индексирования

- У каждого физического диска — своя очередь и своё число читателей: NVMe и SATA SSD — 4,
  USB SSD — 2, HDD — 2, USB-HDD и облачные диски — 1. Две буквы на одном физическом диске — одна
  очередь. Таблица — `src/planirovshchik.rs`.
- Потоков разбора текста — по числу ядер: разбор дороже чтения.
- Очередь HDD читается в порядке обхода папок. Сортировка по номеру MFT — возможное улучшение
  (до ~1,4 раза на мелких файлах), пока не сделана.
- Индекс лучше писать не на диск, который сейчас читается, если есть сопоставимый по скорости
  другой: запись на тот же диск замедляет его чтение почти втрое.

## Проверка планировщика (26.10.2026)

Программа `zamer_indeksa`: индексирование папок замера на C:, D:, P: (36 078 файлов, 2,8 ГБ по
размеру) в новую папку данных на C:; перед каждым прогоном файлы вытесняются из кэша Windows
(`--holodno`), сборка release.

| Прогон | Режим | Время, с |
|---|---|---|
| 1 | общая очередь | 70,7 |
| 2 | очереди по дискам | 46,7 |
| 3 | общая очередь | 44,1 |
| 4 | очереди по дискам | 45,3 |

Первый прогон медленнее из-за холодных служебных записей файловой системы (MFT): их
`--holodno` не вытесняет, и после первого прогона они в памяти у обоих режимов. На тёплых
записях режимы равны (44–47 с, ~800 файлов/с): на этой смеси предел не в дисках, а дальше по
конвейеру (разбор и запись индекса). Планировщик не замедляет; выигрыш ожидается при холодных
записях и большой доле HDD — это пока не измерено.

## Оговорки

- Замер одной машины. Числа читателей выбраны по форме кривых (где рост останавливается),
  они переносятся на другие машины лучше, чем сами МБ/с.
- Подгонка USL на части наборов слабая (R² у C: с крупными файлами — 0,19); для решений взята
  таблица по k, а не формула.
- В 163 из 192 ячеек свежие файлы кончались и чтение шло по кругу; кэш Windows обойдён, но
  буфер самого диска мог помогать — сильнее всего это касается HDD на мелких файлах.

## Как повторить

```
cargo build --release --bin zamer_diskov
target\release\zamer_diskov podgotovka --disk C: --disk D:
target\release\zamer_diskov opyty --disk C: --disk D: --vyhod zamer.csv --predel-min 12
python tools\model_diskov.py --vhod zamer.csv --dokument model.md --json model.json
target\release\zamer_diskov ochistka --disk C: --disk D:
```

`--tolko-plan` печатает план без опытов; `--bystro` — проверочный прогон за 1–2 минуты.
